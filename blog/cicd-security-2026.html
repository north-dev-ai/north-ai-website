CI/CD Security Best Practices 2026

Published by North AI | DevSecOps Expert | 16 min read

CI/CD pipelines are the most attacked vector in modern software supply chains. In 2026, securing your pipelines isn't optional—it's survival. This guide covers the threats and how to defend against them.

🚨 Reality Check:

  • 67% of organizations experienced a supply chain attack in 2025
  • Average breach cost: $4.5M
  • CI/CD pipelines have full access to your code, secrets, and infrastructure

The 7 Biggest CI/CD Security Threats

1. Exposed Secrets in Pipelines

The Threat: API keys, database passwords, and tokens hardcoded or logged in CI/CD runs.

Real example:

# BAD - Secret exposed in logs
- name: Deploy
  run: |
    echo "Deploying with key: ${{ secrets.API_KEY }}"
    deploy.sh

The Fix:

# GOOD - Use secrets properly
- name: Deploy
  env:
    API_KEY: ${{ secrets.API_KEY }}
  run: deploy.sh
  # Secret never appears in logs

Best Practices:

  • ✅ Use platform secrets management (GitHub Secrets, GitLab Variables)
  • ✅ Rotate secrets every 90 days
  • ✅ Use secret scanning tools (GitHub Advanced Security)
  • ✅ Never log secrets, even accidentally
  • ✅ Use short-lived tokens when possible

2. Supply Chain Poisoning

The Threat: Attackers inject malicious code via dependencies or GitHub Actions.

Attack vector:

# Vulnerable - uses unversioned action
- uses: some-org/deploy-action@main  # ❌ Main branch can change!

# Secure - pins to commit SHA
- uses: some-org/deploy-action@abc123def  # ✅ Immutable

Defense checklist:

  • ✅ Pin all actions to commit SHAs, not tags
  • ✅ Review action source code before using
  • ✅ Use Dependabot to track action updates
  • ✅ Enable dependency review on PRs
  • ✅ Scan container images for vulnerabilities

3. Privilege Escalation

The Threat: CI/CD runners have excessive permissions.

Bad configuration:

permissions: write-all  # ❌ Nuclear option!

Secure configuration:

permissions:
  contents: read      # Can read repo
  packages: write     # Can publish packages
  pull-requests: read # Can read PRs
  # Everything else: denied by default

4. Code Injection via Pull Requests

The Threat: Untrusted PR runs with repository secrets.

⚠️ CRITICAL: Never run untrusted code with secrets!

# DANGEROUS - PR from fork has access to secrets
on:
  pull_request:  # ❌ Includes forks!

# SAFER - Require approval for forks
on:
  pull_request_target:  # Only approved PRs

Better approach:

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  test:
    runs-on: ubuntu-latest
    # NO secrets here - just testing
    
  deploy:
    # Only on main branch, after merge
    if: github.ref == 'refs/heads/main'
    needs: test
    # Secrets OK here

5. Insecure Runner Configuration

The Threat: Self-hosted runners with excessive access or outdated software.

Self-hosted runner security:

  • ❌ Don't use same runner for public and private repos
  • ❌ Don't run as root
  • ❌ Don't persist data between jobs
  • ✅ Use ephemeral runners (spin up, run job, destroy)
  • ✅ Keep runner software updated
  • ✅ Network-isolate runners (no internet access if possible)

Secure Secrets Management

GitHub Secrets (Encrypted Environment Variables)

# Set secret in GitHub UI: Settings → Secrets → Actions

# Use in workflow
env:
  DATABASE_URL: ${{ secrets.DATABASE_URL }}
  API_KEY: ${{ secrets.API_KEY }}

HashiCorp Vault Integration

- name: Import Secrets
  uses: hashicorp/vault-action@v2
  with:
    url: https://vault.company.com
    token: ${{ secrets.VAULT_TOKEN }}
    secrets: |
      secret/data/prod api_key | API_KEY
      secret/data/prod db_pass | DB_PASS

AWS Secrets Manager

- name: Configure AWS
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/GitHubActions
    aws-region: us-east-1

- name: Get Secrets
  run: |
    aws secretsmanager get-secret-value \
      --secret-id prod/api-key \
      --query SecretString \
      --output text

Secret Rotation Strategy:

  1. Use automated rotation (AWS/Vault support this)
  2. Set expiration alerts (30 days before expiry)
  3. Maintain secret access logs
  4. Revoke immediately on suspected compromise

Audit and Compliance

Enable Audit Logging

# GitHub Enterprise: full audit trail
# Track:
# - Who triggered workflows
# - What secrets were accessed
# - Changes to workflow files
# - Failed authentication attempts

Require Code Review

# .github/workflows/deploy.yml
on:
  push:
    branches: [main]

# Branch protection rules:
# ✅ Require PR reviews (min 2 approvers)
# ✅ Require status checks
# ✅ No force push
# ✅ Require signed commits

Workflow Approval for Sensitive Operations

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production  # Requires manual approval
    steps:
      - name: Deploy to prod
        run: ./deploy.sh

Configure in GitHub: Settings → Environments → Production → Required reviewers

Container Security

Scan Images for Vulnerabilities

- name: Build image
  run: docker build -t myapp:${{ github.sha }} .

- name: Scan with Trivy
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: myapp:${{ github.sha }}
    severity: 'CRITICAL,HIGH'
    exit-code: '1'  # Fail build on vulnerabilities

Sign Container Images

- name: Sign image
  uses: sigstore/cosign-installer@main

- run: |
    cosign sign --key cosign.key \
      myregistry.io/myapp:${{ github.sha }}

Network Security

Restrict Outbound Network Access

# Self-hosted runner: configure firewall
# Allow only:
# - Package registries (npm, PyPI)
# - Deployment targets
# - Logging/monitoring endpoints
# Block everything else

Use Private Networking

# Deploy via VPN or AWS PrivateLink
# Never expose deployment endpoints to public internet

Compliance Checklist 2026

  1. ✅ Secrets: No hardcoded secrets, all in encrypted storage
  2. ✅ Actions: Pinned to commit SHAs, reviewed before use
  3. ✅ Permissions: Minimal required, explicitly defined
  4. ✅ PRs: Untrusted code runs without secrets
  5. ✅ Runners: Ephemeral, isolated, non-root
  6. ✅ Audit: All workflow runs logged and monitored
  7. ✅ Images: Scanned for vulnerabilities before deploy
  8. ✅ Network: Outbound traffic restricted
  9. ✅ Approvals: Production deploys require manual review
  10. ✅ Rotation: Secrets rotated every 90 days
