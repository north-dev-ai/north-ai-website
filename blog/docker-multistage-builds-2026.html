Docker Multi-Stage Builds: Cut Image Size by 80%

Published: October 12, 2026 | By North AI | 8 min read

Your Docker images are probably 5-10x larger than they need to be. That means slower deployments, higher storage costs, and bigger security attack surfaces.

Multi-stage builds fix this. They let you compile your app in one stage with all the build tools, then copy only the production artifacts to a minimal final image. The result? 70-90% smaller images with zero changes to your app code.

The Problem: Bloated Docker Images

Most Dockerfiles do everything in one stage:

FROM node:18
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build
CMD ["node", "dist/index.js"]

This works, but the final image includes:

  • All npm dev dependencies (TypeScript, webpack, testing libs)
  • Source files that were compiled
  • Build tools you don't need at runtime
  • Cached layers from intermediate build steps

❌ Single-Stage

Image size: 1.2 GB
Layers: 15
CVEs: 47
Deploy time: 3m 20s

✅ Multi-Stage

Image size: 180 MB
Layers: 8
CVEs: 12
Deploy time: 45s

Multi-Stage Build Basics

Here's the same Dockerfile using multi-stage builds:

# Stage 1: Build
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:18-slim
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY package*.json ./
RUN npm ci --production
CMD ["node", "dist/index.js"]

What changed:

  • Stage 1 (builder): Full Node.js image with all dev tools
  • Stage 2 (final): Slim Node.js image, only copies built artifacts
  • --from=builder: Copies files from first stage
  • Result: Final image has no dev dependencies or source files

Real-World Examples

Node.js/TypeScript API

# Build stage
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json tsconfig.json ./
RUN npm ci
COPY src ./src
RUN npm run build && npm prune --production

# Production stage  
FROM node:18-alpine
RUN apk add --no-cache dumb-init
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package*.json ./
USER node
EXPOSE 3000
CMD ["dumb-init", "node", "dist/index.js"]
Pro tip: Use dumb-init to properly handle signals in containers. It ensures your app shuts down cleanly.

Python FastAPI Application

# Build stage
FROM python:3.11 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Production stage
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
USER nobody
CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

Go Binary (Smallest Possible)

# Build stage
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY go.* ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o app

# Production stage (scratch = empty image!)
FROM scratch
COPY --from=builder /app/app /app
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
EXPOSE 8080
CMD ["/app"]
Go magic: Compiled Go binaries can run in a scratch image (literally empty). Final image is just your binary - often under 10 MB!

Java Spring Boot

# Build stage
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# Production stage
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]

Advanced Techniques

Multiple Build Stages

You can use more than two stages:

# Stage 1: Dependencies
FROM node:18 AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

# Stage 2: Build
FROM node:18 AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

# Stage 3: Test
FROM node:18 AS test
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm test

# Stage 4: Production
FROM node:18-slim
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=deps /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]

Conditional Stages with Build Args

FROM node:18 AS base
WORKDIR /app
COPY package*.json ./

FROM base AS development
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]

FROM base AS production
RUN npm ci --production
COPY dist ./dist
CMD ["node", "dist/index.js"]

Build for development or production:

# Development
docker build --target development -t app:dev .

# Production
docker build --target production -t app:prod .

Best Practices

1. Use Specific Base Images

❌ Don't:
FROM node:18
Size: 990 MB
✅ Do:
FROM node:18-alpine
Size: 175 MB

2. Order Layers by Change Frequency

# Good: dependencies change less often than code
COPY package*.json ./
RUN npm ci
COPY . .

# Bad: code changes invalidate npm ci cache
COPY . .
RUN npm ci

3. Clean Up in the Same Layer

# Each RUN creates a layer
RUN apt-get update && \
    apt-get install -y curl && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*

4. Don't Copy Unnecessary Files

Use .dockerignore:

node_modules
npm-debug.log
.git
.env
*.md
tests/
.vscode/

5. Run as Non-Root

FROM node:18-alpine
RUN addgroup -g 1001 appuser && \
    adduser -D -u 1001 -G appuser appuser
WORKDIR /app
COPY --chown=appuser:appuser . .
USER appuser
CMD ["node", "index.js"]

Common Mistakes

Mistake 1: Copying node_modules Between Stages

Bad: COPY --from=builder /app/node_modules from a full Node image to alpine
Problem: Native binaries won't work across different base images
Fix: Run npm ci in the final stage

Mistake 2: Not Using .dockerignore

Without .dockerignore, every COPY . . includes node_modules, .git, and other junk. This invalidates cache and slows builds.

Mistake 3: Installing Dev Dependencies in Production

# Bad
RUN npm install

# Good
RUN npm ci --production

Measuring the Impact

Before deploying, check your image size:

docker images myapp:latest

REPOSITORY   TAG      SIZE
myapp        latest   180MB  ← multi-stage

Check layer count and CVEs:

docker history myapp:latest | wc -l
docker scan myapp:latest

When NOT to Use Multi-Stage

Multi-stage builds aren't always worth it:

  • Simple scripts: If your image is already tiny (Python script with 3 packages), don't over-optimize
  • Local development only: If you never deploy this image, single-stage is simpler
  • Monolithic build process: If your build genuinely needs everything at runtime

Conclusion

Multi-stage Docker builds are the easiest win in container optimization. You get:

  • 70-90% smaller images
  • Faster deployments
  • Fewer security vulnerabilities
  • Lower storage costs

The setup takes 10 minutes. The savings compound forever.
