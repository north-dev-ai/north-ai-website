Terraform vs CloudFormation 2026: Which IaC Tool Wins?

Published: October 12, 2026 | By North AI | 10 min read

You need Infrastructure as Code. Manual cloud resource management doesn't scale and leads to configuration drift.

The two dominant IaC tools are Terraform (HashiCorp) and AWS CloudFormation. Both provision infrastructure, but they take fundamentally different approaches. This guide helps you pick the right one in 2026.

Quick Comparison

Feature Terraform CloudFormation
Multi-cloud ✅ AWS, Azure, GCP, 3000+ providers ❌ AWS only
Language HCL (readable, concise) JSON/YAML (verbose)
State Separate state file (S3, Terraform Cloud) Managed by AWS (automatic)
Cost Free (OSS), Terraform Cloud paid tiers Free (AWS service)
Drift detection Manual (terraform plan) Built-in (drift detection)
Learning curve Moderate (HCL + state concepts) Steep (verbose YAML, nested logic)
Community Huge (open source) AWS-specific

Use Terraform If...

  • You use multiple cloud providers (AWS + GCP + Azure)
  • You want readable, maintainable code (HCL > YAML)
  • You need to manage non-AWS resources (GitHub, Datadog, PagerDuty)
  • You value community modules and tooling
  • You're willing to manage state files

Use CloudFormation If...

  • You're 100% AWS and will never leave
  • You want AWS-native integration (no external state)
  • You need SAM for serverless (Lambda, API Gateway)
  • You want automatic drift detection
  • You prefer AWS managing everything

Example: Create an EC2 Instance

Terraform (HCL)

# main.tf
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  
  tags = {
    Name = "web-server"
    Environment = "production"
  }
}

output "instance_ip" {
  value = aws_instance.web.public_ip
}

Deploy:

terraform init
terraform plan
terraform apply

CloudFormation (YAML)

# template.yaml
AWSTemplateFormatVersion: '2010-09-09'
Description: 'EC2 instance'

Resources:
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: ami-0c55b159cbfafe1f0
      InstanceType: t3.micro
      Tags:
        - Key: Name
          Value: web-server
        - Key: Environment
          Value: production

Outputs:
  InstanceIP:
    Description: Public IP
    Value: !GetAtt WebServer.PublicIp

Deploy:

aws cloudformation deploy \
  --template-file template.yaml \
  --stack-name web-server-stack
Winner: Terraform - HCL is more readable and concise. CloudFormation's YAML is verbose and harder to maintain.

State Management

Terraform State

Terraform tracks infrastructure in a terraform.tfstate file:

# Store state in S3 (team-friendly)
terraform {
  backend "s3" {
    bucket = "mycompany-terraform-state"
    key    = "prod/terraform.tfstate"
    region = "us-east-1"
    
    # State locking with DynamoDB
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

Pros:

  • Portable (works anywhere)
  • Version controlled (S3 versioning)
  • Locking prevents concurrent changes

Cons:

  • You must manage state storage
  • State file contains secrets (encrypt it!)
  • State corruption can happen

CloudFormation State

CloudFormation manages state automatically - you never see it.

Pros:

  • Zero state management work
  • AWS handles everything
  • Built-in drift detection

Cons:

  • Locked to AWS
  • Less control over state
  • Harder to troubleshoot state issues
Winner: CloudFormation - for AWS-only teams. No state management beats managing state yourself.

Multi-Cloud Support

Terraform: True Multi-Cloud

# Provision AWS + GCP + GitHub in one config
provider "aws" {
  region = "us-east-1"
}

provider "google" {
  project = "my-project"
  region  = "us-central1"
}

provider "github" {
  token = var.github_token
}

# AWS S3 bucket
resource "aws_s3_bucket" "data" {
  bucket = "myapp-data"
}

# GCP Cloud Storage bucket
resource "google_storage_bucket" "backups" {
  name     = "myapp-backups"
  location = "US"
}

# GitHub repository
resource "github_repository" "app" {
  name        = "myapp"
  description = "My application"
}

One terraform apply provisions everything across AWS, GCP, and GitHub.

CloudFormation: AWS Only

CloudFormation cannot provision non-AWS resources. Period.

If you need multi-cloud or third-party integrations, CloudFormation is not an option.

Modules & Reusability

Terraform Modules

# modules/vpc/main.tf
variable "cidr_block" {
  type = string
}

resource "aws_vpc" "main" {
  cidr_block = var.cidr_block
  enable_dns_hostnames = true
}

output "vpc_id" {
  value = aws_vpc.main.id
}

# Use the module
module "production_vpc" {
  source     = "./modules/vpc"
  cidr_block = "10.0.0.0/16"
}

module "staging_vpc" {
  source     = "./modules/vpc"
  cidr_block = "10.1.0.0/16"
}

Terraform Registry has 3,000+ community modules ready to use:

# Use community EKS module
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "19.0.0"
  
  cluster_name    = "my-cluster"
  cluster_version = "1.28"
}

CloudFormation Nested Stacks

# parent-stack.yaml
Resources:
  VPCStack:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: https://s3.amazonaws.com/templates/vpc.yaml
      Parameters:
        CIDRBlock: 10.0.0.0/16

Nested stacks work but are more cumbersome than Terraform modules.

Winner: Terraform - module system is cleaner, and the registry has thousands of ready-made modules.

CI/CD Integration

Terraform in GitHub Actions

name: Terraform Deploy

on:
  push:
    branches: [main]

jobs:
  terraform:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v3
      
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
      
      - name: Terraform Init
        run: terraform init
      
      - name: Terraform Plan
        run: terraform plan -out=tfplan
      
      - name: Terraform Apply
        if: github.ref == 'refs/heads/main'
        run: terraform apply tfplan

CloudFormation in GitHub Actions

name: CloudFormation Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v3
      
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
      
      - name: Deploy CloudFormation stack
        run: |
          aws cloudformation deploy \
            --template-file template.yaml \
            --stack-name myapp \
            --capabilities CAPABILITY_IAM

Both integrate cleanly with CI/CD. Roughly equal.

Real-World Migration Example

Scenario: You Have CloudFormation, Want Terraform

Step 1: Import existing resources

# Generate Terraform config from existing AWS resources
$ cf2tf template.yaml > main.tf

# Import existing resources into Terraform state
$ terraform import aws_instance.web i-1234567890abcdef0
$ terraform import aws_vpc.main vpc-0a1b2c3d4e5f6

Step 2: Verify plan shows no changes

$ terraform plan
No changes. Infrastructure is up-to-date.

Step 3: Delete CloudFormation stack (retain resources)

$ aws cloudformation delete-stack \
    --stack-name myapp \
    --retain-resources

Now Terraform manages your existing AWS resources without recreating anything.

When to Use Both

Some teams use both:

  • Terraform: Manage AWS accounts, VPCs, IAM, cross-cloud resources
  • CloudFormation (SAM): Deploy serverless apps (Lambda, API Gateway, DynamoDB)

AWS SAM (built on CloudFormation) is genuinely better than Terraform for serverless:

# SAM template - deploy Lambda + API Gateway in 10 lines
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31

Resources:
  HelloWorldFunction:
    Type: AWS::Serverless::Function
    Properties:
      Runtime: nodejs18.x
      Handler: index.handler
      Events:
        HelloWorld:
          Type: Api
          Properties:
            Path: /hello
            Method: get

Deploy with sam deploy - it handles packaging, uploading to S3, and CloudFormation stack creation.

Common Mistakes

1. Not Storing Terraform State Remotely

Bad: Local terraform.tfstate file
Problem: Team members can't collaborate, state gets out of sync
Fix: Use S3 backend with DynamoDB locking

2. Hardcoding Values

# Bad
resource "aws_instance" "web" {
  instance_type = "t3.micro"  # Hardcoded
}

# Good
variable "instance_type" {
  type    = string
  default = "t3.micro"
}

resource "aws_instance" "web" {
  instance_type = var.instance_type
}

3. No Drift Detection

Run terraform plan weekly to catch manual changes:

# GitHub Actions - weekly drift check
on:
  schedule:
    - cron: '0 9 * * 1'  # Every Monday 9am

jobs:
  drift-check:
    runs-on: ubuntu-latest
    steps:
      - run: terraform plan -detailed-exitcode
      # Exits 2 if drift detected

2026 Recommendation

Choose Terraform

  • Multi-cloud strategy
  • Need third-party integrations
  • Want readable code (HCL)
  • Value community modules
  • Greenfield projects

Choose CloudFormation

  • 100% AWS, forever
  • Heavy serverless (Lambda/SAM)
  • Want zero state management
  • Already AWS-native shop
  • Existing CFN stacks

Conclusion

In 2026, Terraform wins for most teams:

  • Multi-cloud flexibility (even if you're AWS-only today)
  • Better language (HCL > YAML)
  • Stronger community and ecosystem
  • More third-party integrations

CloudFormation still makes sense for:

  • Serverless apps (use SAM)
  • Teams deeply committed to AWS-native tooling
  • Organizations that can't manage external state

The good news? Both are free, both work well, and you can migrate between them if needed.
