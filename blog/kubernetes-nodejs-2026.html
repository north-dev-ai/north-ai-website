Kubernetes + Node.js: Complete Deployment Guide 2026

Published by North AI | DevOps Expert | 14 min read

Kubernetes is the standard for running Node.js apps at scale in 2026. This guide shows you how to deploy production-ready Node.js applications with proper configuration, autoscaling, and zero-downtime updates.

Why Kubernetes for Node.js?

  • Auto-scaling: Handle traffic spikes automatically
  • Self-healing: Crashed containers restart instantly
  • Zero-downtime: Rolling updates with health checks
  • Multi-cloud: Run anywhere (AWS, GCP, Azure, on-prem)
  • Resource efficiency: Pack more apps per server

Prerequisites

You'll need:

  • Docker image of your Node.js app (see my Docker guide)
  • Kubernetes cluster (minikube locally, EKS/GKE/AKS for production)
  • kubectl CLI installed

Basic Deployment Manifest

Save as deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nodejs-app
  labels:
    app: nodejs-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nodejs-app
  template:
    metadata:
      labels:
        app: nodejs-app
    spec:
      containers:
      - name: nodejs-app
        image: your-registry/nodejs-app:1.0.0
        ports:
        - containerPort: 3000
        env:
        - name: NODE_ENV
          value: "production"
        - name: PORT
          value: "3000"
        resources:
          requests:
            memory: "256Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 10
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5

Deploy it:

kubectl apply -f deployment.yaml

What this does:

  • ✅ Runs 3 replicas (high availability)
  • ✅ Sets resource limits (prevents one app hogging all CPU)
  • ✅ Health checks (auto-restart unhealthy pods)
  • ✅ Readiness checks (no traffic to starting pods)

Service (Internal Load Balancer)

Expose your deployment with a Service:

apiVersion: v1
kind: Service
metadata:
  name: nodejs-service
spec:
  selector:
    app: nodejs-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 3000
  type: ClusterIP

This creates an internal load balancer at nodejs-service:80 within the cluster.

Ingress (External Access)

To expose your app to the internet with a domain:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nodejs-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.yourdomain.com
    secretName: nodejs-tls
  rules:
  - host: api.yourdomain.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: nodejs-service
            port:
              number: 80

Requires: NGINX Ingress Controller + cert-manager for free SSL

Secrets Management

Never hardcode secrets! Use Kubernetes Secrets:

# Create secret from file
kubectl create secret generic app-secrets \
  --from-literal=DATABASE_URL=postgres://user:pass@host/db \
  --from-literal=JWT_SECRET=your-secret-key

# Reference in deployment
env:
- name: DATABASE_URL
  valueFrom:
    secretKeyRef:
      name: app-secrets
      key: DATABASE_URL

ConfigMaps (Non-Secret Config)

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"
---
# Reference in deployment
envFrom:
- configMapRef:
    name: app-config

Horizontal Pod Autoscaler

Scale based on CPU usage automatically:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nodejs-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nodejs-app
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

Behavior: When CPU > 70%, scale up. When CPU drops, scale down.

Rolling Updates (Zero Downtime)

Update strategy in deployment:

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

How it works:

  1. Start 1 new pod (maxSurge: 1)
  2. Wait for readiness check to pass
  3. Terminate 1 old pod
  4. Repeat until all pods updated

Deploy new version:

kubectl set image deployment/nodejs-app \
  nodejs-app=your-registry/nodejs-app:1.1.0

# Watch rollout
kubectl rollout status deployment/nodejs-app

# Rollback if needed
kubectl rollout undo deployment/nodejs-app

Resource Optimization

Set correct requests/limits to avoid wasted resources:

resources:
  requests:
    memory: "256Mi"  # Guaranteed allocation
    cpu: "250m"      # 0.25 CPU cores
  limits:
    memory: "512Mi"  # Hard limit (OOM kill if exceeded)
    cpu: "500m"      # Throttled if exceeded

Finding right values:

  • Start conservative (256Mi/250m)
  • Monitor actual usage with kubectl top pods
  • Adjust based on real metrics

Production Checklist

  1. ✅ Health checks configured (liveness + readiness)
  2. ✅ Resource limits set
  3. ✅ Multiple replicas (min 3)
  4. ✅ Autoscaling enabled
  5. ✅ Secrets in Kubernetes Secrets (not env vars)
  6. ✅ Rolling update strategy
  7. ✅ Monitoring (Prometheus + Grafana)
  8. ✅ Logging (Fluentd/EFK stack)
  9. ✅ Network policies (restrict pod communication)
  10. ✅ Pod Disruption Budgets (prevent too many pods down)

Debugging Commands

# View pods
kubectl get pods

# Pod logs
kubectl logs -f pod-name

# Describe pod (events, status)
kubectl describe pod pod-name

# Execute command in pod
kubectl exec -it pod-name -- /bin/sh

# Port forward for local testing
kubectl port-forward pod-name 3000:3000

# View resource usage
kubectl top pods
kubectl top nodes

Cost Optimization

  • Right-size resources: Don't over-provision CPU/memory
  • Use spot instances: 60-80% cheaper for non-critical workloads
  • Cluster autoscaler: Scale nodes down during low traffic
  • Namespace resource quotas: Prevent runaway resource usage
