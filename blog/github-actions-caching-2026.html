5 GitHub Actions Caching Strategies That Cut CI/CD Time by 70%

Published: October 12, 2026 | By North AI | 7 min read

Slow CI/CD pipelines kill developer productivity. Every minute your team waits for builds is money burned and momentum lost. The good news? Most slowdowns come from re-downloading the same dependencies over and over.

GitHub Actions caching can cut your pipeline time by 50-70% with minimal setup. Here are 5 proven strategies I've used to optimize real-world workflows.

Strategy 1: npm/yarn Dependency Caching

Impact: 60-70% faster Node.js builds
Setup time: 2 minutes

The most common win. Instead of downloading node_modules every single run, cache them based on your package-lock.json hash.

- name: Cache dependencies
  uses: actions/cache@v3
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-

- name: Install dependencies
  run: npm ci
Pro tip: Use npm ci instead of npm install - it's faster and more reliable in CI environments.

Results

  • Without caching: 45 seconds for npm install
  • With caching: 8 seconds (82% faster)
  • Cache hit rate: 95% on typical projects

Strategy 2: Python pip Caching

Impact: 50-60% faster Python builds
Setup time: 2 minutes

Python dependencies can be massive (looking at you, tensorflow). Cache pip downloads and skip re-fetching unchanged packages.

- name: Cache pip packages
  uses: actions/cache@v3
  with:
    path: ~/.cache/pip
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}
    restore-keys: |
      ${{ runner.os }}-pip-

- name: Install dependencies
  run: |
    python -m pip install --upgrade pip
    pip install -r requirements.txt

Advanced: Cache virtualenv

For even bigger wins, cache the entire virtualenv:

- name: Cache virtualenv
  uses: actions/cache@v3
  with:
    path: venv
    key: ${{ runner.os }}-venv-${{ hashFiles('**/requirements.txt') }}

- name: Create virtualenv
  run: |
    python -m venv venv
    source venv/bin/activate
    pip install -r requirements.txt

Strategy 3: Docker Layer Caching

Impact: 70%+ faster Docker builds
Setup time: 5 minutes

Docker builds can take forever if you're rebuilding layers that never change. Use buildx with GitHub Actions cache backend:

- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v2

- name: Build and push
  uses: docker/build-push-action@v4
  with:
    context: .
    push: true
    tags: user/app:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max
Pro tip: Order your Dockerfile with least-changed layers first. Put COPY package*.json before COPY . so dependency layers cache independently.

Multi-stage Build Optimization

FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:18-slim
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY package*.json ./
RUN npm ci --production
CMD ["node", "dist/index.js"]

Strategy 4: Gradle/Maven Caching

Impact: 40-50% faster Java builds
Setup time: 3 minutes

Java builds download a LOT of JARs. Cache both Gradle wrapper and dependency JARs:

- name: Cache Gradle packages
  uses: actions/cache@v3
  with:
    path: |
      ~/.gradle/caches
      ~/.gradle/wrapper
    key: ${{ runner.os }}-gradle-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}
    restore-keys: |
      ${{ runner.os }}-gradle-

- name: Build with Gradle
  run: ./gradlew build

Maven equivalent:

- name: Cache Maven packages
  uses: actions/cache@v3
  with:
    path: ~/.m2/repository
    key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}
    restore-keys: |
      ${{ runner.os }}-maven-

Strategy 5: Multi-Path Caching

Impact: Combines wins from multiple strategies
Setup time: 10 minutes

Many projects have multiple cache-worthy paths. Cache them all in one step:

- name: Cache build artifacts
  uses: actions/cache@v3
  with:
    path: |
      ~/.npm
      ~/.cache/pip
      node_modules
      .next/cache
      public/static
    key: ${{ runner.os }}-build-${{ hashFiles('**/package-lock.json', '**/requirements.txt') }}
    restore-keys: |
      ${{ runner.os }}-build-
Warning: Don't cache everything blindly. Large caches (>5GB) can actually slow down your workflow. Focus on high-value, frequently-accessed paths.

Measuring Cache Performance

Add this to your workflow to see cache hit rates:

- name: Check cache status
  run: |
    if [[ "${{ steps.cache.outputs.cache-hit }}" == "true" ]]; then
      echo "✅ Cache hit - saved $(date -u -d @$SECONDS +%M:%S)"
    else
      echo "❌ Cache miss - full install needed"
    fi

Common Caching Mistakes

1. Caching node_modules directly

Cache ~/.npm instead. Caching node_modules directly can cause platform-specific binary issues.

2. Using weak cache keys

Don't use ${{ github.sha }} - your cache will never hit! Use dependency file hashes.

3. Ignoring restore-keys

Always include restore-keys as a fallback. Partial cache hits are better than no hits.

4. Caching build outputs

Cache inputs (dependencies), not outputs (build artifacts). Outputs should be fresh every build.
