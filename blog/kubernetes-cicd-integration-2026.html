Kubernetes CI/CD Integration: Complete Guide for 2026

Published: October 12, 2026 | By North AI | 10 min read

Deploying to Kubernetes manually is slow, error-prone, and doesn't scale. CI/CD automation fixes this - but integrating Kubernetes with your pipeline isn't straightforward.

This guide shows you how to build production-ready Kubernetes CI/CD pipelines in 2026. We'll cover deployment strategies, GitOps, Helm charts, and security best practices.

Why Kubernetes + CI/CD?

Manual Kubernetes deployments mean:

  • Running kubectl apply from your laptop
  • Forgetting which environment has which version
  • Config drift between clusters
  • No rollback strategy when things break
  • Developers with production kubeconfig files (scary)

CI/CD automation gives you:

  • Every deploy is tested, versioned, and auditable
  • One-click rollbacks
  • Environment parity (dev matches prod)
  • No manual kubectl access needed
  • Gradual rollouts with health checks

Two Approaches: Push vs GitOps

Push-Based (Traditional)

CI/CD runs kubectl apply

Pros:
  • Simple to understand
  • Works with any CI/CD tool
  • No extra infrastructure
Cons:
  • CI needs cluster credentials
  • No drift detection
  • Can't self-heal

GitOps (Modern)

Cluster pulls from Git

Pros:
  • Cluster is always in sync with Git
  • Self-healing
  • No credentials in CI
  • Full audit trail
Cons:
  • Requires ArgoCD/Flux
  • Learning curve
  • More moving parts

Recommendation: Start with push-based for simplicity. Move to GitOps when you have 3+ environments or multiple clusters.

Push-Based CI/CD (GitHub Actions)

Step 1: Store kubeconfig Securely

Never commit kubeconfig files. Store as GitHub Secret:

# Get your kubeconfig (base64 encoded)
cat ~/.kube/config | base64

# Add to GitHub Secrets as KUBECONFIG_BASE64

Step 2: Build and Push Docker Image

name: Deploy to Kubernetes

on:
  push:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v3
      
      - name: Log in to Container Registry
        uses: docker/login-action@v2
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Build and push Docker image
        uses: docker/build-push-action@v4
        with:
          context: .
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest

Step 3: Deploy to Kubernetes

      - name: Set up kubectl
        uses: azure/setup-kubectl@v3
        with:
          version: 'v1.28.0'
      
      - name: Configure kubectl
        run: |
          echo "${{ secrets.KUBECONFIG_BASE64 }}" | base64 -d > kubeconfig
          export KUBECONFIG=kubeconfig
      
      - name: Deploy to Kubernetes
        run: |
          export KUBECONFIG=kubeconfig
          
          # Update image tag in deployment
          kubectl set image deployment/myapp \
            myapp=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
          
          # Wait for rollout
          kubectl rollout status deployment/myapp
          
          # Check deployment
          kubectl get pods -l app=myapp
Pro tip: Use kubectl rollout status to wait for deployment to complete. It exits with error if rollout fails, failing your CI job.

Using Helm Charts

Helm templates your Kubernetes manifests. Better than raw YAML for:

  • Environment-specific values
  • Reusable components
  • Versioned releases

Basic Helm Chart Structure

myapp/
├── Chart.yaml
├── values.yaml
├── values-prod.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml

values.yaml (defaults)

replicaCount: 2

image:
  repository: ghcr.io/myorg/myapp
  tag: latest
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 100m
    memory: 128Mi

values-prod.yaml (production overrides)

replicaCount: 5

resources:
  limits:
    cpu: 1000m
    memory: 1Gi
  requests:
    cpu: 200m
    memory: 256Mi

ingress:
  enabled: true
  host: myapp.example.com

Deploy with Helm in CI/CD

      - name: Deploy with Helm
        run: |
          export KUBECONFIG=kubeconfig
          
          helm upgrade --install myapp ./helm/myapp \
            --namespace production \
            --create-namespace \
            --values helm/myapp/values-prod.yaml \
            --set image.tag=${{ github.sha }} \
            --wait \
            --timeout 5m
Warning: Always use --wait with Helm. Without it, Helm considers deployment successful even if pods crash immediately.

GitOps with ArgoCD

GitOps inverts the model: instead of CI pushing to Kubernetes, Kubernetes pulls from Git.

How It Works

  1. CI builds Docker image, pushes to registry
  2. CI updates Git repo with new image tag
  3. ArgoCD detects Git change
  4. ArgoCD syncs Kubernetes cluster to match Git

Install ArgoCD

kubectl create namespace argocd
kubectl apply -n argocd -f \
  https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Get admin password
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d

Create ArgoCD Application

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp
  namespace: argocd
spec:
  project: default
  
  source:
    repoURL: https://github.com/myorg/myapp-config
    targetRevision: main
    path: helm/myapp
    helm:
      valueFiles:
        - values-prod.yaml
  
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

CI/CD Updates Image Tag

      - name: Update image tag in Git
        run: |
          git clone https://github.com/myorg/myapp-config
          cd myapp-config
          
          # Update values.yaml with new tag
          yq eval ".image.tag = \"${{ github.sha }}\"" -i helm/myapp/values-prod.yaml
          
          git config user.name "CI Bot"
          git config user.email "ci@example.com"
          git add helm/myapp/values-prod.yaml
          git commit -m "Update image to ${{ github.sha }}"
          git push

ArgoCD sees the Git change and automatically deploys. No kubectl credentials in CI!

Deployment Strategies

1. Rolling Update (Default)

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 1 extra pod during deploy
      maxUnavailable: 0  # Never have fewer than desired

Best for: Most apps. Zero downtime, gradual rollout.

2. Blue-Green Deployment

# Deploy new version (green)
kubectl apply -f deployment-v2.yaml

# Test green version
kubectl port-forward deployment/myapp-v2 8080:80

# Switch traffic to green
kubectl patch service myapp -p '{"spec":{"selector":{"version":"v2"}}}'

# Delete blue when confident
kubectl delete deployment myapp-v1

Best for: When you need instant rollback capability.

3. Canary Deployment

Route 10% of traffic to new version, gradually increase:

# Deploy canary (10% of pods)
kubectl scale deployment myapp-v2 --replicas=1
kubectl scale deployment myapp-v1 --replicas=9

# Monitor metrics
# If good, increase canary
kubectl scale deployment myapp-v2 --replicas=5
kubectl scale deployment myapp-v1 --replicas=5

# Eventually replace all
kubectl scale deployment myapp-v2 --replicas=10
kubectl delete deployment myapp-v1

Best for: High-risk changes. Minimizes blast radius.

Health Checks and Readiness

Always configure liveness and readiness probes:

spec:
  containers:
  - name: myapp
    image: myapp:latest
    
    livenessProbe:
      httpGet:
        path: /health
        port: 8080
      initialDelaySeconds: 30
      periodSeconds: 10
      failureThreshold: 3
    
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 5
      failureThreshold: 2
Difference:
- Liveness: Is the app running? If not, restart the pod.
- Readiness: Is the app ready for traffic? If not, remove from load balancer.

Secrets Management

Don't commit secrets to Git! Use External Secrets Operator:

Store secrets in cloud provider

# AWS Secrets Manager
aws secretsmanager create-secret \
  --name myapp/database-url \
  --secret-string "postgresql://..."

ExternalSecret syncs to Kubernetes

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: myapp-secrets
spec:
  refreshInterval: 1h
  
  secretStoreRef:
    name: aws-secrets-manager
    kind: SecretStore
  
  target:
    name: myapp-secrets
    creationPolicy: Owner
  
  data:
  - secretKey: database-url
    remoteRef:
      key: myapp/database-url

Now your app uses myapp-secrets like a normal Kubernetes secret, but values come from AWS.

Resource Limits (Critical!)

Always set resource requests and limits:

resources:
  requests:
    cpu: 100m      # Guaranteed CPU
    memory: 128Mi  # Guaranteed memory
  limits:
    cpu: 500m      # Max CPU (throttled if exceeded)
    memory: 512Mi  # Max memory (OOMKilled if exceeded)
Without limits: One misbehaving pod can steal all cluster resources and crash everything. Always set them!

Multi-Environment Strategy

Separate manifests for each environment:

kubernetes/
├── base/
│   ├── deployment.yaml
│   └── service.yaml
├── overlays/
│   ├── dev/
│   │   └── kustomization.yaml
│   ├── staging/
│   │   └── kustomization.yaml
│   └── prod/
│       └── kustomization.yaml

base/deployment.yaml (shared)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:latest

overlays/prod/kustomization.yaml (overrides)

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

bases:
  - ../../base

replicas:
  - name: myapp
    count: 10

images:
  - name: myapp
    newTag: v1.2.3

Deploy with kustomize

kubectl apply -k kubernetes/overlays/prod

Monitoring Deployments

Add these checks to your CI/CD:

# Wait for rollout
kubectl rollout status deployment/myapp

# Check pod status
kubectl get pods -l app=myapp

# Check recent events
kubectl get events --sort-by=.metadata.creationTimestamp | tail -20

# Check logs of new pods
kubectl logs -l app=myapp --tail=50

# Rollback if needed
kubectl rollout undo deployment/myapp

Common Mistakes

1. Using :latest tag

Bad: image: myapp:latest
Problem: Kubernetes can't tell if image changed. No rollback capability.
Fix: Use Git SHA or semantic version: image: myapp:a1b2c3d

2. No resource limits

Leads to cluster instability. Always set requests and limits.

3. Deploying to prod untested

Deploy to dev first, run tests, then promote to prod. Never skip environments.

4. Direct kubectl access

Developers shouldn't run kubectl against prod. Use GitOps or restricted CI/CD pipelines.

Complete GitHub Actions Example

name: Deploy to Production

on:
  push:
    tags:
      - 'v*'

jobs:
  deploy:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v3
      
      - name: Extract version
        id: version
        run: echo "VERSION=${GITHUB_REF#refs/tags/}" >> $GITHUB_OUTPUT
      
      - name: Build and push image
        uses: docker/build-push-action@v4
        with:
          push: true
          tags: ghcr.io/myorg/myapp:${{ steps.version.outputs.VERSION }}
      
      - name: Set up kubectl
        uses: azure/setup-kubectl@v3
      
      - name: Configure kubectl
        run: echo "${{ secrets.KUBECONFIG_BASE64 }}" | base64 -d > kubeconfig
      
      - name: Deploy with Helm
        run: |
          export KUBECONFIG=kubeconfig
          
          helm upgrade --install myapp ./helm/myapp \
            --namespace production \
            --values helm/myapp/values-prod.yaml \
            --set image.tag=${{ steps.version.outputs.VERSION }} \
            --wait --timeout 5m
      
      - name: Verify deployment
        run: |
          export KUBECONFIG=kubeconfig
          kubectl rollout status deployment/myapp -n production
          kubectl get pods -n production -l app=myapp
      
      - name: Notify on failure
        if: failure()
        run: |
          echo "Deployment failed! Rolling back..."
          helm rollback myapp -n production

Kubernetes CI/CD integration gives you:

  • Automated, tested deploys

  • One-click rollbacks
  • Full audit trail
  • Self-healing with GitOps

Start simple with push-based deployments and Helm. Move to GitOps (ArgoCD) when you manage multiple clusters or need strict compliance.
